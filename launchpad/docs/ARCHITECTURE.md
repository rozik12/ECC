# Архитектура

```
 вы ── браузер / lp / curl ──► Control plane (1..N копий) ◄── Postgres
 GitHub ── вебхук push ──────►        ▲   │ routes
                                      │   ▼
                      heartbeat,   Agent (по одному на узел) ── Docker
                      статусы, логи       ▲ порты контейнеров
                                          │
 интернет ── HTTP/HTTPS ──► Edge ─────────┘
```

## Компоненты

- **Control plane** (`internal/api`, `internal/store`, `internal/scheduler`): API, панель, вебхук,
  состояние. Хранилище: файл для одного сервера, Postgres для нескольких копий. Планировщик работает
  только на лидере (`pg_try_advisory_lock` на отдельном соединении, блокировка пропадает вместе с
  упавшей копией).
- **Agent** (`internal/agent`): раз в 3 секунды отправляет статусы и логи, получает сервисы узла и
  приводит контейнеры к ним (reconcile). Сборка идёт в отдельном потоке, чтобы долгий build не выглядел
  как падение узла. Агент сам ходит к control plane, поэтому ему не нужны входящие порты.
- **Edge** (`internal/edge`): опрашивает маршруты и проксирует по заголовку Host. Сам получает сертификаты
  Let's Encrypt (`x/crypto/acme/autocert`) только для хостов из таблицы маршрутов. При ошибке опроса
  оставляет последнюю рабочую таблицу.
- **Build** (`internal/build`): определяет язык и генерирует Dockerfile вне дерева репозитория.
- **Web** (`internal/web`): панель на чистом JS, вшита в бинарник, CSP без inline.
- **CLI** (`internal/cli`): клиент API.

## Версии и деплой без простоя

Каждое изменение (переменные, настройки, редеплой, откат, push) вызывает `Service.Bump`: растёт
`revision` и в `history` записывается снимок настроек (до 20 штук).

1. Агент видит новую ревизию и запускает её рядом со старой (`lp-<id>-<rev>`).
2. Пока новая не прошла проверку здоровья, она в состоянии `starting`. Агент продолжает сообщать
   о старой как о `running`.
3. Control plane направляет трафик на самую новую ревизию в состоянии `running`
   (`store.Live`). Статусы приходят по каждой ревизии отдельно, поэтому провал новой не отключает старую.
4. Когда новая здорова, старая живёт ещё 10 секунд (edge обновляет маршруты раз в 3 секунды), затем удаляется.
5. Если новая не здорова за 60 секунд, она удаляется и записывается ошибка, повтор через минуту.

Исключение: сервис с томами останавливает старую ревизию до запуска новой. Два контейнера не должны
писать в один том, цена этого решения короткий простой.

## Откат

В снимок попадает образ, настройки, переменные и (после первой сборки) точный коммит, который
сообщил агент. Откат создаёт новую ревизию из снимка и для Git-сервиса закрепляет коммит
(`pin_commit`). Следующий redeploy или push снимает закрепление. Ревизию, которая ни разу не
собиралась, откатить нельзя.

## Логи

Агент раз в цикл читает `docker logs --since` каждого контейнера (первый раз последние 100 строк),
отправляет строки в heartbeat. Control plane проверяет, что сервис назначен этому узлу, и хранит
последние 2000 строк на сервис. Клиенты читают с курсором `after`.

## Решения и компромиссы

- Go и стандартная библиотека. Внешние зависимости: драйвер Postgres и `x/crypto` (ACME).
- Docker CLI вместо SDK: аргументы массивом без shell, всё пользовательское проверяется в
  `model.Service.Validate`.
- Агент тянет (pull), control plane никогда не подключается к узлам.
- Часы копий control plane должны быть синхронизированы (NTP): `last_seen` узла сравнивается с
  локальным временем каждой копии.
- Статусы и логи это мягкое состояние: после перезапуска восстанавливаются из heartbeat.

## Дальше

1. **Изоляция сборок:** выделенные builder-узлы, rootless/gVisor, кеш слоёв, реестр по умолчанию.
2. **Сеть:** приватная сеть между сервисами (WireGuard), внутренние имена, TCP-прокси для баз данных.
3. **Данные:** шаблоны Postgres/Redis/MySQL, бэкапы томов, перенос томов между узлами.
4. **Наблюдаемость:** метрики CPU/RAM/трафик, алерты, поиск по логам, долгое хранение.
5. **Продукт:** проекты и окружения, превью-окружения для pull request, команды и права, OAuth.
6. **Надёжность:** реплика Postgres, несколько edge с общим хранилищем сертификатов, rate limit API.
7. **Бизнес:** учёт ресурсов, квоты, биллинг.
