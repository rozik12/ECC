# Архитектура и план

## Компоненты

```
 пользователь ──► Control plane ◄── heartbeat ── Agent (узел 1..N) ── Docker
                       │ routes                          ▲
                       ▼                                 │ порты контейнеров
                     Edge ◄───────── трафик из интернета ─┘
```

- **Control plane** хранит желаемое состояние (сервисы) и назначает им узлы.
- **Agent** раз в 3 секунды отправляет статусы и получает список сервисов узла,
  затем приводит контейнеры к этому списку (reconcile). Сборка идёт отдельным
  потоком, чтобы долгий build не выглядел как падение узла.
- Каждое изменение сервиса увеличивает `revision`. Новая ревизия поднимается
  рядом, старая удаляется после успешного старта. Статус старой ревизии
  не попадает в маршруты.
- **Edge** опрашивает маршруты и проксирует по заголовку Host.

## Этапы

1. **Ядро (сделано):** сервисы, узлы, планировщик, агент, edge, деплой из образа/Git.
2. **Надёжность (сделано):** Postgres вместо файла, несколько реплик control plane
   с выбором лидера через advisory lock, проверка здоровья перед переключением
   маршрута, деплой без простоя. Не сделано: отказоустойчивость самого Postgres и edge
   (нужны реплика БД и несколько edge за балансировщиком), откат на предыдущую версию
   по команде.
3. **Сборки:** отдельные builder-узлы с изоляцией, автоопределение языка
   (Nixpacks/Buildpacks), реестр образов, кеш слоёв.
4. **Наблюдаемость:** логи (сбор агентом, стрим в API), метрики CPU/RAM, события.
5. **Сеть:** автоматический HTTPS (Caddy on-demand TLS или ACME), свои домены,
   приватная сеть между сервисами (WireGuard).
6. **Данные:** тома, шаблоны баз данных (Postgres, Redis), бэкапы.
7. **Продукт:** панель (React), CLI, GitHub-интеграция с автодеплоем по push,
   проекты и окружения, команды и права, превью-окружения.
8. **Бизнес:** учёт ресурсов, лимиты, биллинг.

## Принятые решения

- Go и стандартная библиотека: один бинарник на компонент, мало зависимостей.
- Docker CLI вместо SDK: аргументы идут массивом без shell, поля пользователя
  проверяются в `model.Service.Validate`.
- Файловое хранилище остаётся режимом для одного сервера. Оба хранилища проходят один
  набор тестов (`internal/store/store_test.go`).
- Трафик идёт на самую новую здоровую версию (`store.Live`). Статусы приходят от агента
  по каждой версии отдельно, поэтому провал новой версии не отключает старую.
- Лидер-выборы через `pg_try_advisory_lock` на отдельном соединении: блокировка
  освобождается сама, если реплика умерла.
- Часы реплик должны быть синхронизированы (NTP): `last_seen` узла сравнивается с
  локальным временем каждой реплики.
