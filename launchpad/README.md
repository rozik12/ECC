# Launchpad

Собственный аналог Railway: вы указываете образ или Git-репозиторий, а платформа
запускает сервис на одном из ваших серверов, держит его живым и отдаёт по домену.

## Что уже работает

- **Control plane** (`cmd/lp-controlplane`): API, хранение состояния, планировщик.
- **Agent** (`cmd/lp-agent`): ставится на каждый сервер, запускает контейнеры через Docker.
- **Edge** (`cmd/lp-edge`): принимает трафик и направляет его по домену на нужный сервер.
- Деплой из Docker-образа или из Git (нужен `Dockerfile` в репозитории).
- Переменные окружения, редеплой, удаление.
- Если сервер перестал отвечать, сервисы переезжают на другой.
- **Деплой без простоя:** новая версия запускается рядом со старой. Трафик переключается
  только после того, как новая прошла проверку здоровья. Если не прошла за 60 секунд,
  старая продолжает работать, а в статусе видна ошибка.
- **Postgres и несколько реплик control plane:** состояние лежит в базе, планировщик
  работает только на одной реплике (выбирается автоматически, при её падении
  подхватывает другая).

Не реализовано: HTTPS (ставьте Caddy перед edge), панель, логи, тома, базы данных
как шаблоны, пользователи и биллинг. Порядок работ описан в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Запуск

```bash
go build -o bin/ ./cmd/...

export LP_API_TOKEN=$(openssl rand -hex 24)   # для вас (API)
export LP_NODE_TOKEN=$(openssl rand -hex 24)  # для агентов и edge

# 1. Control plane. Один сервер: состояние хранится в файле.
./bin/lp-controlplane --domain apps.example.com
#    Несколько реплик: общая база Postgres (запустите команду на нескольких машинах).
LP_DATABASE_URL=postgres://user:pass@db:5432/launchpad ./bin/lp-controlplane --domain apps.example.com

# 2. На каждом сервере с Docker (addr — адрес, по которому edge достучится до сервера)
./bin/lp-agent --control-plane http://CP:8080 --addr 10.0.0.5

# 3. Edge на публичном сервере (wildcard DNS *.apps.example.com -> этот сервер)
./bin/lp-edge --control-plane http://CP:8080 --listen :80
```

Создать сервис:

```bash
curl -H "Authorization: Bearer $LP_API_TOKEN" -d '{"name":"web","image":"nginx:1","port":80}' \
  http://CP:8080/api/v1/services
curl -H "Authorization: Bearer $LP_API_TOKEN" http://CP:8080/api/v1/services
```

Сервис станет доступен на `web.apps.example.com`.

### Проверка здоровья

По умолчанию сервис считается готовым, когда порт принимает соединения. Если указать
`"health_path":"/healthz"`, платформа запрашивает этот адрес, и любой ответ кроме 5xx
считается здоровым. Состояние видно в поле `state`: `pending`, `building`, `starting`,
`running` или `failed`. Пока новая версия не `running`, поле `serving_revision` показывает,
какая версия сейчас принимает трафик.

### Редеплой и переменные

```bash
curl -X POST -H "Authorization: Bearer $LP_API_TOKEN" http://CP:8080/api/v1/services/ID/redeploy
curl -X PUT  -H "Authorization: Bearer $LP_API_TOKEN" -d '{"KEY":"value"}' http://CP:8080/api/v1/services/ID/env
```

## Безопасность

- Порты контейнеров публикуются на всех интерфейсах узла. Закройте их файрволом
  так, чтобы к ним мог ходить только edge.
- Токены передаются открытым текстом, пока перед control plane нет TLS.
- Сборка чужого кода выполняется на узле. Для публичной платформы нужна изоляция
  сборок (отдельный builder) — см. план.

## Тесты

```bash
go test ./...
# вместе с Postgres:
LP_TEST_DATABASE_URL="postgres://user@localhost:5432/lp_test" go test ./...
```

Тесты стирают таблицы в указанной базе, используйте отдельную пустую базу.

Проверено: планировщик и переезд сервисов, логика агента на подставном Docker
(включая деплой без простоя и откат при неудачной версии), API-цепочка деплоя,
одинаковое поведение файлового хранилища и Postgres, выбор лидера между репликами,
запуск двух реплик на одной базе. Работа с настоящим Docker пока не проверялась.
