# Launchpad

Собственный аналог Railway. Вы указываете Docker-образ или Git-репозиторий, а платформа
запускает сервис на одном из ваших серверов, держит его живым, отдаёт по домену с HTTPS
и обновляет без простоя.

## Возможности

| Что | Как работает |
|-----|--------------|
| Деплой из образа или Git | Нужен `Dockerfile`. Если его нет, платформа сама определяет Node.js, Python, Go или статический сайт |
| Несколько серверов | Планировщик ставит сервис на наименее загруженный узел. Если узел замолчал, сервисы переезжают |
| Деплой без простоя | Новая версия стартует рядом со старой. Трафик переключается, только когда она прошла проверку здоровья |
| Откат | Любую из последних 20 версий можно вернуть одной командой: тот же образ, тот же коммит, те же переменные |
| Автодеплой по push | Подписанный вебхук GitHub (HMAC-SHA256) |
| Логи | Агент собирает вывод контейнеров, API и панель показывают его в реальном времени |
| Домены и HTTPS | Домен `имя.ваш-домен` из коробки, свои домены через CNAME, сертификаты Let's Encrypt выпускаются автоматически |
| Тома | Постоянное хранилище на узле. Сервис с томом привязан к узлу и перезапускается без перекрытия версий |
| Лимиты | Память, CPU, число процессов, ротация логов контейнера |
| Панель и CLI | Веб-панель встроена в control plane. Консольная утилита `lp` |
| Несколько копий control plane | Общая база Postgres, планировщик работает на одной копии, при её падении подхватывает другая |

Чего пока нет, см. [раздел ниже](#что-ещё-не-сделано).

## Быстрый старт

Нужны: Go 1.24 (для сборки), Docker на рабочих узлах, Postgres для нескольких копий control plane
(для одного сервера хватит файла).

```bash
go build -o bin/ ./cmd/...

export LP_API_TOKEN=$(openssl rand -hex 24)   # для вас: API, панель, lp
export LP_NODE_TOKEN=$(openssl rand -hex 24)  # для агентов и edge

# 1. Control plane (панель на http://localhost:8080)
./bin/lp-controlplane --domain apps.example.com
#    с Postgres и несколькими копиями:
LP_DATABASE_URL=postgres://user:pass@db:5432/launchpad ./bin/lp-controlplane --domain apps.example.com

# 2. На каждом рабочем сервере с Docker и git.
#    --addr: адрес, по которому edge достучится до этого сервера
./bin/lp-agent --control-plane http://CP:8080 --addr 10.0.0.5

# 3. Edge на публичном сервере. DNS: *.apps.example.com -> этот сервер
./bin/lp-edge --control-plane http://CP:8080 --listen :80 --https-listen :443 --acme-email you@example.com
```

Готовые файлы развёртывания: [`deploy/docker-compose.yml`](deploy/docker-compose.yml)
(control plane + Postgres + edge), [`deploy/lp-agent.service`](deploy/lp-agent.service) (systemd для узла),
[`deploy/Dockerfile`](deploy/Dockerfile). Эти файлы проверены только на корректность синтаксиса, образ
не собирался.

## Работа с сервисами

```bash
export LP_URL=http://CP:8080 LP_API_TOKEN=...

lp deploy web --image nginx:1.27 --port 80 --health /
lp deploy api --git https://github.com/you/api --ref main --port 3000 -e DATABASE_URL=postgres://...
lp ls                                   # состояния и версии
lp logs api -f                          # логи в реальном времени
lp env api LOG_LEVEL=debug --unset OLD  # изменить переменные (создаёт новую версию)
lp redeploy api
lp rollback api 3                       # вернуться к версии 3
lp domains api add app.example.com      # затем CNAME app.example.com -> api.apps.example.com
lp webhook api                          # адрес и секрет для GitHub
lp rm api
```

То же самое доступно в веб-панели и по HTTP API (`/api/v1/...`, заголовок `Authorization: Bearer $LP_API_TOKEN`).

### Состояния

`pending` (ещё не назначен или агент не ответил) → `building` (сборка или загрузка образа) →
`starting` (контейнер запущен, ждём здоровья) → `running` или `failed`.
Пока новая версия не `running`, поле `serving_revision` показывает, какая версия принимает трафик.
Если новая версия не стала здоровой за 60 секунд, она удаляется, а старая продолжает работать.

### Проверка здоровья

По умолчанию достаточно, чтобы порт принимал соединения. С `health_path` платформа делает
`GET` на этот путь, любой ответ кроме 5xx считается здоровым.

### Сборка из Git

Репозиторий забирается на глубину 1 (ветка, тег или коммит), хуки и подмодули отключены.
Дальше:

| Что найдено | Что делает платформа |
|-------------|----------------------|
| `Dockerfile` | Собирает его как есть |
| `package.json` | Node 22. npm, pnpm или yarn по lock-файлу. Шаг `build`, если он есть. Запуск: `Procfile` (`web:`), иначе `start`, иначе `main` |
| `requirements.txt` / `pyproject.toml` | Python 3.12. Запуск: `Procfile`, иначе `app.py`, иначе `main.py` |
| `go.mod` | Версия Go из `go.mod`. Собирает пакет `main` из корня или единственный из `cmd/`. Итоговый образ distroless |
| `index.html` | nginx. Порт сервиса должен быть 80 |

Сгенерированный Dockerfile лежит вне репозитория и его не меняет. Если ничего не подошло, деплой
завершится понятной ошибкой в статусе.

### Тома

`--volume data:/var/lib/app`. Данные лежат на узле сервиса (`lp-<id>-data` в Docker).
Такой сервис не переезжает при падении узла, потому что на новом узле том был бы пустым.
Если узел потерян навсегда, используйте «Reschedule» в панели (`POST .../reschedule`):
данные со старого узла не переносятся. При удалении сервиса тома остаются на узле.

### Образы между узлами

Каждый узел по умолчанию собирает образ сам. Чтобы после переезда не пересобирать, поднимите
Docker-реестр, доступный всем узлам, и запускайте агентов с `--registry host:5000`: собранные
образы будут отправляться туда и браться оттуда. Реестр, его TLS и доступы настраиваете вы.

## Что ещё не сделано

- **Сборки изолированы слабо.** Чужой код собирается через `docker build` на рабочем узле, с лимитом
  памяти и таймаутом 15 минут, но без отдельной песочницы. Для публичной платформы нужны выделенные
  builder-узлы или rootless/gVisor.
- Нет приватной сети между сервисами и баз данных как готовых шаблонов (Postgres/Redis можно
  запустить как обычный сервис с томом, но достучаться до него можно только через опубликованный порт).
- Нет пользователей, команд, прав и биллинга: один общий API-токен.
- Edge и Postgres сами не отказоустойчивы (нужны реплика БД и несколько edge за балансировщиком).
  Сертификаты хранятся в `--cert-dir` одного edge.
- Логи хранятся последние 2000 строк на сервис, без поиска по времени и метрик.
- Нет TLS на самом control plane: ставьте перед ним обратный прокси или привязывайте к localhost.
- Real Docker: код запуска контейнеров, сборки и логов покрыт только тестами на подставном движке,
  см. раздел «Проверено».

## Безопасность

- Порты контейнеров публикуются на всех интерфейсах узла. Закройте их файрволом так, чтобы к ним мог
  ходить только edge.
- `LP_NODE_TOKEN` общий для всех агентов и edge. Утечка даёт возможность подделывать статусы и логи.
- Агент имеет доступ к Docker-сокету, то есть фактически root на узле. Не открывайте его портов
  (он их не слушает) и не запускайте на машинах с чужими данными.
- Токены передаются открытым текстом, пока перед control plane нет TLS.
- Всё, что попадает в командную строку `docker`/`git` (имя, образ, ref, переменные, тома), проверяется
  до сохранения. Команды запускаются массивом аргументов, без shell.
- Панель отдаётся с политикой CSP без inline-скриптов, текст из API выводится только как текст.
- Вебхук GitHub проверяет подпись HMAC-SHA256. Для неизвестного сервиса и неверной подписи ответ одинаковый.
- Свои домены нельзя занять дважды и нельзя взять под вашим базовым доменом. Сертификаты выпускаются только
  для доменов, у которых есть работающий сервис.

## Проверено

```bash
go test ./...
# и вместе с Postgres (тест очищает таблицы, используйте пустую отдельную базу):
LP_TEST_DATABASE_URL="postgres://user@localhost:5432/lp_test" go test -race ./...
```

Автоматически проверяется: планировщик и переезд, закрепление сервисов с томами, логика агента
(деплой без простоя, откат при неудачной версии, тома, логи, коммиты), API, подпись вебхука, домены,
откат, определение языка сборки, edge, консольная утилита, одинаковое поведение файлового хранилища и
Postgres, выбор лидера. Сквозной тест (`internal/e2e`) поднимает настоящие control plane, два агента
и edge на сокетах и подтверждает: деплой, 100+ запросов во время выкатки версии без единой ошибки,
переезд на другой узел после падения. Сломанная логика выбора версии этот тест валит.

Веб-панель просмотрена в браузере (светлая и тёмная темы, телефонная ширина), ошибок в консоли нет.

**Не проверено на живой системе:** запуск настоящих контейнеров, `docker build`, `git fetch` с GitHub,
выпуск сертификатов Let's Encrypt, Docker-образ из `deploy/Dockerfile`. Эти части написаны аккуратно,
но первые запуски на настоящем сервере стоит делать с наблюдением за логами агента.
